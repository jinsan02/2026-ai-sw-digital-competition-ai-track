# 02 — 핵심 기술 기여 (전문가 심사 40% 대응)

## ① KD 교사 선택 법칙: "강한 교사"가 아니라 "학생이 모르는 걸 아는 교사"

- **발견**: 교사의 train 일치율 ↔ KD 이득이 **완전 단조 역상관**.
  m8(Qwen3.5-0.8B) 0.811 → **+0.0039** / q35-4B 0.870 → +0.0033 / t15(동계열 HCX-1.5B) 0.891 → **−0.011** / m9(9B) 0.9428 → ±0.000
- 큰 교사일수록 train을 외워 로짓이 원핫으로 붕괴 → 가르칠 "이견"이 없음. 동계열 교사는 학생이 이미 아는 것만 앎 → CE 희석 비용만 지불.
- **교사 가치 = 라벨과 다른 의견의 양 × 이견의 이질성(타 계열)**. 신규 교사 후보는 train 일치율 먼저 측정(0.9+ 위험 / ~0.8 이상적)이라는 사전 게이트까지 도출.
- 최종장에서 **앙상블 자기증류**(트리오 0.7966을 통째 teacher로 → 학생 1개로 압축)가 이 법칙의 완성형: 배포 계열과 동족이면서 seed-다양성 dark knowledge를 보유한 첫 "엄격히 더 강한" 교사 → main-swap으로 **+0.0006** (0.7966→0.7972).

## ② Consensus Sieve × 조건부 α — 행 단위 신뢰도 기반 학습 제어

- OOF에서 독립 모델 3개(m7/m8/v6)의 합의 수 c∈{0,1,2,3}를 행마다 계산 → **backbone gradient를 c에 따라 0/0.25/0.75/1로 스케일** (합의 낮은 행 = 라벨 노이즈 의심 → 표현학습 손상 방지).
- 약한 4개 클래스(read/grep/list/glob) 행만 distill-α 0.5→0.7 (조건부 α) — 교사 의존을 필요한 곳에만.
- 단독 기여 최대 레버: sieve 도입으로 0.7896→**0.7939** (+0.0043).

## ③ 후처리 룰 스택 — 전 룰 OOF 5-fold × 교차시드 게이트

- 후보 룰 수십 개 중 **5-fold(시드 2개 교차) 전부에서 rescue>harm인 것만** 배포. 예: R1h(patch→edit) 83플립 83R/0H/0N 완전체.
- **s202 transfer gate**: 룰을 개발용 시드(s42)가 아니라 **배포 main(s202)의 자체 OOF 표면**에서 재측정 후 승격 — s42에서 +0.0005였던 soft prior가 s202에서 음성이라 기각된 실사례. "레버는 배포물 위에서 검증한다"는 원칙.
- 룰 스택 합계 Public 기여 ≈ +0.0023 (0.7943→0.7966), 5-fold dF1 +0.0015~+0.0029 all-positive, 룰 간 충돌(2룰 이상 터치 행) 0건.

## ④ 1GB/10분 제약 하 앙상블 — 저장 코덱 + 저마진 라우팅

- **자체 int8 row-wise 저장 코덱**(fp16 1132MB→568MB, argmax 충실도 99.6%) + int4 group-128(→292MB, 멤버용)로 **0.5B 3개를 1GB 안에**.
- 시간은 저마진 라우팅으로 해결: main margin<1.0 행(34.1%)만 멤버 2개 통과 → 3모델인데 7:15 (최종팩 amhyb 실측).
- int4 전면화는 실측 기각(argmax 94.5% — 0.6B에선 열화 과대) → **용량이 아니라 시간이 진짜 제약**임을 규명하고 int8 유지.

## ⑤ Main-swap Best-of-N — 재학습 없는 챔피언 갱신 파이프라인

- 검증된 챔피언팩(룰+멤버 고정)에서 **main 무게만 교체**해 재zip → 빌드 0분, 단일변수 A/B.
- 이 파이프라인으로 마지막 밤 KD 시드 3개(s42/s909/s7070)를 병렬 생산(A100+4070+Colab 3머신) → best-of-N 추첨 → **최종 0.7977 팩도 seed7070 산출물**.
- 부산물 실증: c0a8_swap이 챔피언과 소수 10자리 동률 = 동일 레시피 멤버 교체는 예측 0행 변화 → **멤버축 탐색 조기 종료** 근거 확보 (제출 슬롯 절약).

## ⑥ 시간예산 역산 엔지니어링

- 서버 채점 로그로 **추론시간 = f(실제 토큰 수)** 를 회귀 (v5 6:55/m7 8:55 = 토큰비 0.80과 일치) → 동적 패딩 확인 → "len 캡 줄이기"는 시간 절감 0이라는 반직관 결론.
- 이 산식으로 후보 아키텍처의 서버 시간을 **제출 전에 예측** — 시간초과 실패는 초기 2건(의도된 probe) 이후 0건.
